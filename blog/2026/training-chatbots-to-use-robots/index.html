How to train chatbots to use robots

September 27, 2026

LLMs have suddenly surpassed dedicated robotic models in performing spatial tasks. How might you train an LLM in this way?

I ran a set of simulated robot experiments to find out what data actually enables greater learning of visuospatial capabilities in LLMs. This takes the form of an experiment to find the best textual representation of the robotic scene, also known as the structured state. I then propose an annotation scheme to derive this structured state at scale from video and build out a VLM pipeline for doing that.

So-called LANGUAGE models are increasingly nailing all sorts of visual and spatial tasks. Robotics, 3D design, image generation and more- all going the way of the transformer architecture. This is because, to the computer, text is undoubtedly the universal interface. Everything that the computer understands is ultimately relayed to it via some kind of text. As such, tasks that we perceive as visual can be distilled into textual formats called structured state representations and trained upon to improve visual decision making.

My goal in a set of experiments was to understand what the best makeup for this structured state is, and how to create them at scale to train better models.

The structured state

So what even is this structured state? What does it consist of? Everything? It's supposed to describe the entire visuospatial scene in compact text. In reading a structured state of a scene at some timestep, a model should have all the information it needs to take some action to produce a desired result in the structured state of the NEXT timestep.

Some tasks are expressed in file formats that are sufficiently compact and legible as text that the raw data itself can be used as the bulk of the structured state. This becomes less true as the task widens in context; raw ingestion of every pixel value of Mario Kart to prompt a controller input is not a helpful approach for today’s LLMs, and thus requires a simplified structured state to be easily navigable.

The experiment

My probe to find this ideal structured state for robotics will take an easy case. The robotic tasks I perform will be inside of a simulation engine, and my structured state will derive info from that engine.

In my engine, I can get a report of every object's exact position at every step. This tracking is the bedrock of my structured state. In MuJoCo I read the positions straight from the engine, add a few mm of noise to mimic a real tracker, and store them relative to each other, like where the cube is relative to the gripper.

The state also needs a menu of all possible actions the robot can take at any given timestep. The model's whole job is to choose from it, so that menu constrains what the system can do at all. We define this menu ourselves. These actions can really range in complexity, but let’s first imagine them as fundamental movements like ‘move right’, ‘move down’, ‘move forward’, etc.

And then lastly, the goal label: what the task is and what counts as done. Describing the intent of a task is a very qualitative observation that can be tough to label at scale. Outside of the individual state, you also need to find a clever verifier to score how far you have progressed towards a goal label. This is the metric you hillclimb on in an RL environment to teach a model the whole thing.

I then ran ablative experiments across all of these fields to find which ones actually add meaningful functionality to the model. I wanted to see which fields hurt performance most in their absence, and at what degree of imprecision would the field hurt the model when present.

The planning architecture

Casting multimodal tasks as text prediction has always been possible. Before LLMs supported image inputs, I remember asking LLMs to ‘see’ by giving them ASCII art. GPT2 could’ve taken a list of motor values and predicted something, albeit something bad.

But there have been serious obstacles for a language model to predict motor values at every timestep for a robot. One problem is the huge context-length of predicted values, which can be solved by the concise structured state as well as just having better models with greater attention and context length.

Another such obstacle is that these spatial tasks are way too slow and expensive when carried out by an LLM. The prediction moves at the speed of lengthy response times, but robotic tasks demand real-time reactivity. The LLM has to generate a decision for every step, or else follow some preset plan between refreshes that cannot be adjusted, all while burning tokens.

The System 1/System 2 paradigm of models breaks this limitation. Jev, the heralded System 1 model, can act as a scout, quickly assessing the changes in that structured state over time. Jev relays the changes to the slower, wiser System 2 model, which then rewrites what's left of the plan. Jev simply reads the state, then picks among a limited set of actions defined in the structured state. System 2 makes the initial plan and then, like a watchful guardian, ONLY steps in when Jev assesses from the structured state that there has been a failure in the step or that the task has changed considerably.

An example of System 1/System 2 dynamics. Jev answers ‘how much’ and ‘yes/no’ questions, Sol plays the System 2 role of coach.

With that, the structured state representation of the scene becomes very important for a language model to be able to work through these spatial tasks. The System 2 LLM encodes its decree for Jev within it, and then Jev reads it at every decision. With the LLM generating the high-level directives contained in the state, it can be done live to cover the System 2 role for a task at inference-time, or it can be done offline to make tons of training labels at scale for some class of visual tasks that you can then improve upon.

Trimming the fat

Through ablating the structured state, I distinguished what helped and what didn’t. One such lesson was the heavy-handed importance of tracking. As long as the goal was clearly stated, proposed experimental labels often ended up being totally dominated in usefulness by the tracking data, even accounting for tracking error and noise.

We could distinguish these experimental labels as:

  • Meaning labels: simple yes/no facts computed from the positions: "gripper lined up with the cube", "cube grasped", "cube in the tray"
  • Procedure labels: bookkeeping checks for the task in progress ("is my position estimate out of date?", "how many grab attempts since the last lift?")

These generally went nowhere. The meaning labels describing contact that did survive ablation would reveal a category I might call "fine contact" (i.e. "Is the pen touching the paper?") where a few millimeters of discrepancy can majorly impact the success of the task. In a real task, these labels would require a precision that outstrips tracking error. If tracking error were higher than the precision needed, these "fine contact" interactions would highlight areas that need additional sensors to represent accurately, like recorded haptic feedback.

This ablation gradually whittled down the structured state into a leaner, more useful representation. But most of all, it identified the major defining term of our structured state.

The goal

The goal label mattered way more than any other field beyond tracking. It encodes the whole intent of your task, and you can’t just derive it from some sensor. Someone has to qualitatively evaluate what the task is and when it’s over.

Goals that poorly described ending conditions performed worse than no goal at all. My first pick and place goal said "Pick up the red cube from the table and place it in the blue receptacle." The verifier, however, wanted the arm to retract when done. A good ending condition would therefore not only be in harmony with the intent of the task, but also with the verifier that scores it. That ending condition would also make the model resilient to learning from demos with failed actions like mishandled grabs or premature releases- this experiment revealed the annotation of failed actions to be a very helpful label to collect.

Left: a goal with no ending, and the arm hangs onto the cube over the tray. Right: the goal ends with “then move the gripper clear,” so it lets go and backs away.

One interesting thing: the goal label revealed the coercive control that the action menu could assume. Simple tasks with no goal label even stated could be completed with narrow action menus. With an action menu like [approach, grasp, transport, release and retract] a model will look at a scene with one square block and a bin with a blind assumption that the block should be put in the bin. This is a very very narrow example(what if the actual goal was something way different?) but it exemplifies how the menu subtly encodes the goal on its own and nudges the model in certain directions. Such a narrow menu only works for that single task, but perhaps in the future it could potentially be dynamically tailored to each task by the System 2 model.

Testing intent

Having the model control a robot to paint is a great test. It’s dextrous, can be graded by looking at it, and it’s fun to watch! With the System 2 model tasked with turning the goal into a discrete plan, that plan manifests in the painting task as a list of strokes to draw.

Some initial drawing attempts

I was operating on a few assumptions when structuring how the goal label would best be presented to the model. Robotics has rewarded action-chunking in the past, so it might be good to try breaking down the goal into smaller sub-goals like the individual parts of a painting. Conversely, I also noticed in a lot of computer-use drawing demos that LLMs like to paint in a diffusion-like manner, first filling in the vague blobs of the scene and then iteratively refining at greater detail. I figured it would be good to try breaking the goal down into levels of detail, like first painting larger elements and then adding detail later.

Results of two paintings with different goal structures. ‘One shot’ gives the full plan at once, ‘rounds’ replan at set intervals, ‘parts’ divides the goal by major elements of the image, and coarse-to-fine moves from lowest to highest detail

Take a look! To me, the one-shot illustration performs the best. I found that the plans downstream of broken-down subgoals were badly miscalibrated. The model did not retain an accurate map of where previous strokes actually were, which led to a lot of clutter. Finding a good way to calibrate between subgoals would be vital.

Parts overlapped for a similar reason. With no grounding of the parts within a larger layout, each would drift towards the center, leading to an overlapping mess. Having a persistent layout that maps the parts spatially helped a lot.

The System 2 model can create the initial plan from an image of a painting or just a text prompt, like ‘statue of liberty.’ Here you can see the parts overlapping badly without a layout.

Training on real data

It’s easy to solve a task in a simulator, but we want this model to be able to work in the real world! Our same structured state can teach the model about real life actions if we can reconstruct the necessary labels from regular videos, which would expand capabilities immensely.

Robust video-to-3D software can form the backbone of our tracking reconstruction. These tracking models play a vital role in reconstructing our most valuable signal, so making them as accurate as possible would be a huge focus.

Apart from that, we’d need to create an action menu and a well-defined goal from that same video. To do this, I made an extensive annotation tool called robolabel.

Robolabel is a harness for annotating videos cheaply at scale using any LLM with image support. With it, we can reconstruct both the goal and the action menu at once. The tool structures multiple VLM passes to balance accuracy with cost.

  1. The first pass gets fed a small subset of static frames from the video, and key objects are picked out.
  2. The next pass watches the video at 2FPS and splits the clip into broad action tags like (approach, grasp, transport, release, retract).
  3. Then, a crawl pass explores the neighbors of those previous frames to refine the time boundaries for that action stage.
  4. We run each of these new boundary frames in-order through the VLM to describe the progression of the scene; what happened in this stage? What is touching, visible, or held?
  5. These scene descriptions are read as text to generate highly accurate annotations of the goal

Despite several passes, cost is kept low since the model never actually ingests every frame of the video. The accuracy of annotations, however, turns out much higher in this scaffolded workflow than just ingesting the video raw. It’s the best of both worlds!

We get a clearly defined goal, and the descriptions of each action stage make great subgoals. The action menu can just be populated by the broad action tags we generate in the second pass.

Additionally, we can denote failed action stages, which proved to be a very useful field. If the video has contact or motor values associated with it, those can also be paired to increase accuracy. The experiment is complete with a comparison on cost/speed/quality across several major models. With this, we can now theoretically reconstruct our entire structured state from any video!

Let it rip

So we are now left with our final structured state. Tracking data maps every object in the scene. An action menu encompasses what the model can actually tell the robot to do. A goal with a clear end defines the intent of the task. Additionally, optional contact labels describe haptic data that requires precision beyond the capabilities of the tracking data. Outside of this state lives a verifier that scores how far the model has progressed towards its intended goal.

Our beautiful, platonically-ideal structured state

This covers our full training setup! We create an RL environment and let an LLM loose in it. We define each scene as a structured state, let the model pick from the action menu, and have the verifier score act as the reward function to maximize during training. With a data flywheel that can churn through whatever set of videos you want, we can train the model at a massive scale. I don’t have a fraction of the money to do any of this, but I think this is what the major labs are doing right now. This is how you are able to learn incredible spatial skills through text!
